# Spec 03 — Product Management

**Status:** ✅ Built (2026-10-04) · **Depends on:** 02 (04 for auto-pricing; build 03 + 04 together) · **Server(s):** Admin (write), POS (read-only list)

## 1. Goal
Managers can add, view, edit and deactivate products with an image, name, category, quantity and cost price. MP/SP are filled automatically by the pricing engine (spec 04) and can be edited. The POS can list and look up active products without seeing cost price.

## 2. User stories
- As a **manager**, I add a product with a photo, name, quantity and cost price, and MP/SP appear automatically.
- As a **manager**, I edit any field, including MP/SP, and the change is recorded.
- As a **manager**, I deactivate a product that's no longer sold, without breaking old invoices.
- As a **cashier**, I see a searchable list of products with price and stock, and look one up by code or barcode.

## 3. Scope
**In:** categories, product CRUD, product codes, barcode field, image upload (validate, re-encode, thumbnail), list with search/filter/sort/pagination, soft delete, optimistic locking, initial stock movement, POS read endpoints.
**Out:** stock adjustments after creation (spec 07, `stock_service`), bulk CSV import (backlog), variants/sizes.

## 4. Business rules touched
BR-1, BR-2, BR-3, BR-8, BR-10, BR-12. New:
- **PR-1** Product `code` is generated by the system (`P` + 5 digits from a Postgres sequence `product_code_seq`). It can't be edited and is never reused.
- **PR-2** `barcode`, if given, is unique among all products (including inactive).
- **PR-3** `quantity` can only be set on **create**. After that it changes only through stock movements (spec 07) or sales.
- **PR-4** Name is 2–150 characters and trimmed. Duplicate names are allowed (with a warning) because codes are the identity.

## 5. Data model changes
Migration `0003_catalog`: `categories`, `products` (architecture §5.3, including both CHECK constraints), `stock_movements` (§5.7), `product_code_seq`. Indexes as listed.

## 6. API

### Admin (:5001), role manager+
| Method | Path | Notes |
|---|---|---|
| GET | /api/categories | |
| POST | /api/categories | `{name}` → audit `category.create` |
| GET | /api/products | `?search=&category_id=&low_stock=true&include_inactive=false&page=&page_size=&sort=name\|-updated_at\|quantity` |
| POST | /api/products | `multipart/form-data`: fields + optional `image`. Fields: `name, category_id?, unit, barcode?, description?, quantity, reorder_level, cost_price, market_price?, selling_price?`. If MP/SP are omitted they're auto-calculated. If provided, they're marked manual |
| GET | /api/products/{id} | full `ProductOut` (includes cost, margins, manual flags, version) |
| PATCH | /api/products/{id} | JSON incl. **`version`**. Any of `name, category_id, unit, barcode, description, reorder_level, cost_price, market_price, selling_price, mp_is_manual, sp_is_manual`. `quantity` is not allowed (400 `USE_STOCK_ADJUSTMENT`) |
| POST | /api/products/{id}/image | replace image (old Cloudinary asset deleted after commit) |
| DELETE | /api/products/{id}/image | remove image |
| POST | /api/products/{id}/deactivate · /activate | soft delete / restore |

**PATCH pricing behaviour:** if `cost_price` changes and a price field is **not** manual, it is recalculated with the current settings. Manual fields are kept as they are, and BR-2 is re-checked. If it fails → 422 `PRICE_RULE_VIOLATION` with a message such as "SP ₹250 is below new cost ₹260. Update SP or set it to auto".

**Errors:** 404 `PRODUCT_NOT_FOUND`, 409 `VERSION_CONFLICT` (with `current_version`, `updated_by`, `updated_at`), 409 `BARCODE_TAKEN`, 413 `IMAGE_TOO_LARGE`, 415 `UNSUPPORTED_IMAGE`, 422 `PRICE_RULE_VIOLATION`.

### POS (:5002), role cashier+
| Method | Path | Notes |
|---|---|---|
| GET | /api/products | active only. `PosProductOut`: `id, code, barcode, name, unit, image_url, thumb_url, market_price, selling_price, quantity, low_stock` (**no cost_price**) |

### Images
- Accept JPEG/PNG/WebP, ≤ `MAX_UPLOAD_MB` (4). Open with Pillow + `verify()`, reject anything else (no SVG, because of script risk).
- Strip EXIF, convert to RGB, resize to fit 1024×1024, re-encode as WebP (quality 85) **in memory**. Then upload the bytes to **Cloudinary** (`cloudinary.uploader.upload`) with `folder=CLOUDINARY_FOLDER`, `public_id=<uuid4>`, `overwrite=False`, `resource_type="image"`. Nothing is written to disk, because serverless functions don't have one.
- **Vercel body limit (~4.5 MB):** before uploading, admin-web resizes the photo **in the browser** (canvas → max 1024 px, WebP ~0.85) so a 12 MB phone photo becomes a few hundred KB. The server still validates everything (never trust the client). `MAX_UPLOAD_MB=4`.
- The DB stores `image_public_id`. `media.image_url(public_id, size)` builds CDN URLs with transformations: full `c_limit,w_1024,f_auto,q_auto` and thumb `c_fill,w_256,h_256,f_auto,q_auto`. API responses include `image_url` and `thumb_url`.
- If the DB transaction fails after the upload, delete the Cloudinary asset (compensating action). On replace/remove, delete the old asset **after** the commit succeeds.
- Tests mock the Cloudinary SDK. They never upload for real.

- [ ] Creating "Steel bottle", cost 212, qty 14 with no MP/SP → saved with MP 300, SP 265 (default settings), code `P00001`, one `stock_movements` row `+14 initial`, one audit row `product.create`.
- [ ] Sending a 5 MB file straight to the API (bypassing the browser resize) → 413. A 12 MB phone photo picked in the UI is resized in the browser and uploads fine. Uploading a `.png` that's really a text file → 415.

- [ ] Editing MP to 320 → `mp_is_manual = true`. Changing cost to 230 afterwards → MP stays 320 and SP is recalculated.
- [ ] Setting SP > MP or SP < cost → 422, and nothing changes.
- [ ] Two managers edit the same product. The second save → 409 VERSION_CONFLICT.
- [ ] Deactivated products disappear from POS list and lookup, but stay visible in the admin list with "Show inactive".
- [ ] The POS products response contains **no** `cost_price` key (test asserts on the JSON keys).
- [ ] `PATCH` with `quantity` → 400 `USE_STOCK_ADJUSTMENT`.

## 11. Implementation notes
- Optimistic locking uses SQLAlchemy `version_id_col`. The client also sends `version`, and a mismatch gives 409 with who/when.
- Opening stock is inserted with the product, and a matching `initial` ledger row is written (version starts at 1).
- Each product stores `mp_round_mode` (primary/alternate) so cost changes keep the owner's rounding choice.
- `POST /api/pricing/preview` accepts an optional manual `market_price` so the form can show the matching SP without browser maths.
- The browser resizes photos to ≤1024px WebP before upload (Vercel 4.5 MB limit). The server re-validates.
